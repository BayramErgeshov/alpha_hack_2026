Документ описывает текущую реализацию в `src/data_store.cpp`, `src/analytics.cpp` и `scripts/prepare_data.py`. Рекомендации для следующей версии отмечены отдельно. Все команды выполняются из корня проекта.

Состав поставленных файлов:

|---|---:|---:|---:|

В аналитическом корпусе 9 документов, 64 страницы с непустым текстом, 156 362 символа текста. По текущему `data/analytics/manifest.json` все страницы распознаны методом `windows_ocr`. Эти числа описывают файлы этой поставки; при обновлении данных нужно пересчитать контрольный срез.

Важные особенности исходной выборки:

- 85 525 строк профилей содержат **85 514 уникальных `SYNTHETIC_U`**: 11 повторных строк по идентификатору. Backend сохраняет все строки; доступ по UID возвращает последнюю прочитанную запись. Размеры групп, процентили и количество загруженных компаний считаются по строкам, включая повторы. Поиск может вернуть несколько профилей одного UID. Это текущее поведение, которое нужно учитывать при сверке.
- 18 098 непустых значений `GROUP_ID`; группа задана во всех 85 525 строках. 115 строк имеют выручку от 15 млрд рублей.
- 1 380 585 строк платежей дают 1 380 568 уникальных направленных пар `(PAYER, BENEFICIARY)`; повторяющиеся пары суммируются.
- В платежах 103 695 различных плательщиков и 62 038 различных получателей без профиля в таблице компаний. Это допустимые внешние контрагенты: в API для них `profile_available=false`.
- В таблице связей 11 120 различных `SYNTHETIC_F`, все 12 514 пары `(SYNTHETIC_F, SYNTHETIC_U)` уникальны. 7 885 строк с UID без профиля пропускаются; оставшиеся 4 629 строк относятся к 4 323 уникальным FID. Счётчик отношений внутри backend обозначает уникальные принятые FID, а не число исходных строк и не число пар компаний.

## Повторная подготовка из архивов

Оставьте в корне ровно один архив каждого типа:

```text
Аналитические материалы-20261021T121614Z-1-001.zip
Данные для участников-20261021T121909Z-1-001.zip
```

Скрипт выбирает **первое совпадение** `Аналитические материалы*.zip` и `Данные для участников*.zip`, поэтому несколько версий архивов рядом создают неоднозначность. Храните старые версии вне корня.

```powershell
Set-Location '<папка-проекта>'
python -m pip install -r scripts/requirements.txt
python scripts/prepare_data.py .
```

Только CSV, без OCR:

```powershell
python scripts/prepare_data.py . --data-only
```

Только аналитика на Windows, с уже собранной утилитой `x64/Release/AlphaPdfOcr.exe`:

```powershell
python scripts/prepare_data.py . --analytics-only --ocr windows
```

Если утилита находится в другом месте:

```powershell
python scripts/prepare_data.py . --analytics-only --ocr windows --ocr-executable '.\x64\Release\AlphaPdfOcr.exe' --ocr-language ru
```

На Linux с установленным Tesseract и языками `rus`/`eng`:

```sh
python scripts/prepare_data.py . --analytics-only --ocr tesseract --ocr-language rus+eng
```

`--ocr auto` используется по умолчанию: на Windows сначала выбирается утилита проекта, затем Tesseract из `PATH`. `--ocr none` извлекает только имеющийся текстовый слой. Сначала читается текстовый слой каждой страницы; OCR вызывается только для страницы с полностью пустым извлечённым текстом. Частично прочитанная или повреждённая страница автоматически повторно через OCR не обрабатывается.

Подготовка работает локально и не вызывает платную LLM. CSV копируются из ZIP без преобразований, по точным базовым именам. Если в ZIP несколько файлов с одинаковым базовым именем, используется последнее найденное совпадение. Markdown и manifest заменяются через временный файл, CSV перезаписываются напрямую. Повторный запуск не удаляет старые Markdown, которые исчезли из нового архива.

Не обновляйте набор во время работы сервера. Подготовьте согласованную копию каталогов, проверьте её и перезапустите сервер. Пример запуска и остановки: [RUNBOOK.md](RUNBOOK.md).

## CSV: формат и точные поля

Текущая кодировка договора — UTF-8, разделитель `;`, заголовки чувствительны к регистру. Поддерживаются кавычки `"..."`, удвоенные кавычки `""`, переводы строки внутри заключённого в кавычки поля, окончания строк LF и CRLF. Пробелы и табуляция по краям значений удаляются. Кодировка автоматически не определяется и не преобразуется.

UTF-8 BOM удаляется только из первого заголовка таблицы профилей. Для таблиц платежей и FID-связей сохраняйте UTF-8 **без BOM**. Порядок колонок можно менять: чтение идёт по именам. Дополнительные колонки игнорируются; отсутствие большинства ожидаемых колонок не вызывает ошибку, а превращается в пустые значения. Поэтому проверка схемы до старта обязательна.

## Пустые, нули, числа и флаги

Пустая строка не является подтверждённым отсутствием признака. В текущем загрузчике есть техническая потеря этой разницы:

| Источник | Текущее представление |
|---|---|
| Пустое строковое поле профиля | В большинстве JSON-полей `null` |
| Корректное конечное число с точкой | Число `double` |
| Пустое, неверное число, `NaN`, бесконечность | Внутри `0` |
| Выручка `<=0` | В JSON `annual_revenue_rub=null`, `revenue_available=false` |
| Пустой/неверный платёж | Добавляет сумму/количество `0`; может оставить ребро с нулём |
| `PAY_CNT<=0` | `0`; положительная дробь обрезается к целому |
| Флаг `1`, `1.0`, `true`, `yes`, `да` | `true`; ASCII-регистр нормализуется |
| Любой иной флаг, включая пустое значение | `false` |

Не используйте десятичную запятую или разделители тысяч. Не передавайте `NULL`, `nan`, `None` как текст вместо пустого строкового поля: такие строки останутся значениями. Для флагов безопасный формат — `0.0`/`1.0` или `0`/`1`. Русское `ДА` не гарантируется, поскольку нормализация регистра флагов работает только с ASCII.

В API есть предупреждение `data_quality.warning`, однако `products.*` и `trade.has_fts_data` остаются обычными boolean и не позволяют отличить неизвестное значение от `false`. Платёжные нули также не доказывают отсутствие деятельности: файл платежей мог отсутствовать или не содержать эту компанию.

## Группы, люди, платежи и положение в отрасли

- `group_member_count` — число строк профилей с тем же непустым `GROUP_ID`; для профиля без группы значение по умолчанию `1`.
- `linked_person_record_count` — количество различных принятых FID у компании, после устранения повторов.
- `related_company_count` — объединение других профилей из той же группы и профилей с общим FID. Совпадения по нескольким FID не дублируются, однако множества хранят индексы строк; повторные профили UID могут влиять на счётчик. Транзитивный обход графа не выполняется.
- Платежи суммируются по направленной паре `(PAYER, BENEFICIARY)`. Для известных профилей вычисляются `incoming_amount_rub`, `outgoing_amount_rub` и соответствующие `*_transaction_count`.
- `top_counterparties` — до **8 направлений** с наибольшей суммой, затем количеством платежей. Это общий лимит на входящие и исходящие направления. Один контрагент может появиться дважды, если есть оба направления. Это не восемь уникальных компаний и не полная сеть. Для полных итогов используйте `payment_totals`, а не сумму восьми элементов.
- `profile_available=false` означает отсутствие карточки контрагента; переход к его профилю вернёт `404`. Входящие и исходящие агрегаты известной компании учитывают связи с такими контрагентами.
- `revenue_percentile_in_dataset_industry` — `100 * count(revenue <= current) / count(positive revenues)` среди строк с одинаковыми первыми двумя цифрами ОКВЭД и положительной выручкой. Повторы входят в знаменатель; равные значения получают верхнюю позицию группы равенства.
- Это процентиль в предоставленной выборке, **не доля рынка**. `financials.market_share=null`. Порог крупного бизнеса в кейсе — 15 млрд рублей; `meets_case_large_business_threshold` проверяет выручку относительно него.

Таблица профилей обязательна: при невозможности открыть её или отсутствии записей сервер не стартует. Таблицы платежей и связей технически необязательны: при отсутствии они тихо пропускаются. Не считайте успешный старт доказательством полноты всех трёх файлов.

## Контракт аналитического Markdown

Индекс рекурсивно читает `.md` и `.txt` с расширением в нижнем регистре из `ALFA_ANALYTICS_DIR` (по умолчанию `data/analytics`). Файлы больше 25 MiB пропускаются. JSON manifest, PDF и ZIP индексатор не читает. Не помещайте README и рабочие заметки в каталог корпуса: подходящий `.md` будет принят за банковский источник.

Рекомендуемый текущий формат:

```markdown
# Имя_исходного_документа.pdf
<!-- extraction: pdf_text -->

[[PAGE: 1]]
Текст первой страницы.

[[PAGE: 2]]
Текст второй страницы.
```

Правила загрузки:

- Страницы нумеруются с `1` и соответствуют физическим страницам PDF, включая обложку. Текст до первого маркера не становится доказательством.
- Метод из `<!-- extraction: ... -->` возвращается как `text_extraction`. Без комментария используется `provided_text`. Скрипт записывает `pdf_text`, `windows_ocr`, `tesseract_ocr` либо их объединение через `+`, если методы различались по страницам.
- При смешанных методах API несёт общий метод документа, а `manifest.documents[].pages[].method` позволяет уточнить конкретную страницу.
- Для страницы без текста используйте `<!-- TEXT_UNAVAILABLE -->`. Страницы, содержащие `TEXT_UNAVAILABLE`, не индексируются целиком. Наличие `OCR_REQUIRED:` в любом месте исключает весь файл.
- Файл без `[[PAGE: ...]]` будет целиком считаться страницей 1, если не содержит заглушки. Для PDF так не делайте: потеряется точная привязка страниц.
- Сохраняйте уникальные базовые имена файлов даже в разных подкаталогах: идентификаторы источников используют только имя файла, а не относительный путь.

Индекс делит каждую страницу на фрагменты до примерно **4 200 байт** (не токенов и не символов), предпочитая границы абзацев/пробелов и сохраняя границы UTF-8. Перекрытия между фрагментами нет. Идентификатор имеет вид `Имя.md#page=2#part=3`; номер части растёт в пределах всего документа. Правки предшествующего текста могут поменять `part`, поэтому ID нельзя считать стабильным между версиями корпуса.

OCR искажает цифры, десятичные знаки, проценты, минусы и порядок ячеек таблиц; графики могут дать только подписи. `pages_with_text=64` подтверждает непустой результат, а не точность распознавания. Некоторые обложки содержат лишь десятки символов. Числа и спорные утверждения нужно проверять на исходной странице PDF.

## Manifest и происхождение

Текущий `data/analytics/manifest.json` имеет `schema_version: "1.0"`:

| Поле | Значение |
|---|---|
| `source_archive` | Имя выбранного ZIP |
| `documents[].source_file` | Путь PDF внутри ZIP |
| `documents[].source_sha256` | SHA-256 **сырых байтов исходного PDF**, не Markdown |
| `documents[].text_file` | Имя подготовленного Markdown |
| `documents[].extraction` | Методы извлечения непустого текста документа |
| `documents[].pages[]` | `page`, `method`, `characters` для каждой страницы |
| `documents[].page_count` | Полное число страниц PDF |
| `documents[].pages_with_text` | Число непустых извлечённых страниц |
| `documents[].text_characters` | Сумма символов чистого текста без служебных маркеров |
| `summary` | Суммарные `document_count`, `page_count`, `pages_with_text`, `text_characters` |

`characters` — число Unicode-символов в Python, не размер UTF-8 в байтах. Скрипт нормализует CRLF/CR в LF, удаляет NUL, начальный BOM и пробелы в концах строк.

Backend **не проверяет manifest и SHA-256**: это артефакт контроля происхождения для команды. Сейчас нет хешей ZIP, CSV и результирующего Markdown, времени обработки или версии OCR. При ручной правке Markdown исходный PDF SHA-256 не меняется; зафиксируйте отдельно, что текст был исправлен и кем.

## Обновление корпуса

1. Сохраните исходные ZIP/PDF, текущий manifest и контрольные суммы отдельно от каталога индекса.
2. Подготовьте новый каталог данных. Для добавления PDF добавьте его в единственный выбранный архив аналитики и выполните повторную подготовку. Скрипт не имеет режима добавления одного документа.
3. Проверьте схему CSV, уникальность UID, диапазоны и пропуски. Разберите повторные UID по явному правилу; удаление дублей меняет текущие групповые размеры и процентили.
4. Проверьте manifest, наличие всех Markdown, последовательность страниц и точность нескольких страниц с числами/таблицами. Отсутствующие страницы приводят к ненулевому завершению скрипта; отдельная ошибка OCR может прервать подготовку до обновления manifest.
5. Уберите устаревшие Markdown из **нового** каталога корпуса: скрипт не чистит файлы предыдущей версии. Проверьте, что базовые имена уникальны и служебные документы лежат вне каталога.
6. Передайте согласованный набор backend-команде и перезапустите сервер с `ALFA_DATA_DIR`/`ALFA_ANALYTICS_DIR`, указывающими на него.
7. Проверьте карточку компании, сеть и поиск аналитики. Для этой проверки LLM не нужна.

Оба набора загружаются в память только при старте процесса. Нет API загрузки файлов, изменения профиля или горячего пересоздания индекса. Изменение файла на диске не обновит работающий backend. Перезапуск также очищает сохранённые в памяти разборы и их follow-up контекст.

## Передача командам ИИ и фронта

ИИ-команде передайте версию корпуса, manifest, ограничения периода/полноты данных, перечень исправлений OCR и примеры эталонных цитат. В `GET /api/v1/analytics/search` каждый результат содержит `id`, `document`, `page`, `score`, `text`, `text_extraction`; `items` может быть пустым. Агент запрашивает до 4 фрагментов. Поиск не фильтрует дату публикации: среди материалов есть документ 2021 года, и его нельзя автоматически принимать за текущую позицию банка.

Текущий BM25 использует `k1=1.5`, `b=0.75`, нормализацию регистра ASCII/русского/греческого текста и небольшой русско-английский список стоп-слов. Нет морфологии, синонимов, эмбеддингов, reranker, извлечения таблиц или временного ранжирования. Разные формы русского слова могут не совпасть. `score` — величина ранжирования в этом корпусе, не вероятность, не доверие и не оценка эффекта для компании. Части одного документа могут занимать несколько мест в выдаче.

Фронту передайте трактовку `null`, различие процентили/доли рынка, агрегатов/полной сети и `profile_available`. Для источника показывайте документ, страницу, текст и метод извлечения. API не отдаёт PDF/Markdown как статические файлы и не предоставляет URL скачивания; возможность открытия страницы PDF требует отдельной раздачи исходников и договорённого сопоставления имени Markdown с PDF через manifest.

Общий порядок интеграции: данные → проверенный корпус/профили → backend → API → интерфейс/модель. Приложения не должны самостоятельно пересчитывать суммы восьми контрагентов как полный оборот или переводить диапазоны сотрудников в точные числа.

## Договорённости следующей версии — ещё не реализованы

- Ввести отдельные `dataset_version`/`corpus_version`, хеши ZIP/CSV/Markdown и версии извлечения/OCR, хранить их в manifest и ответах API.
- Проверять обязательные колонки, кодировку, дубли UID и ошибки чисел до загрузки; определить и документировать стратегию дублей.
- Сохранять трёхзначные флаги `true/false/null` и отдельные признаки наличия файлов/полей, чтобы не смешивать неизвестное и ноль.
- Добавить дату документа, язык, отрасль и период данных в структурированные метаданные; версионировать изменения схемы. Сейчас только manifest имеет `schema_version="1.0"`, а OpenAPI — версию `1.0.0`; CSV и ответы данных отдельной версии не содержат.
- Согласовать устойчивые идентификаторы источников на основе хеша/страницы и механизм публикации исходного PDF.
- При необходимости полного графа/истории платежей добавить отдельный контракт; текущий API выдаёт только агрегаты и 8 направлений.

Эти пункты не следует использовать как уже доступные API-возможности. Изменение структуры CSV или ответов сначала согласуйте с backend, ИИ и фронтом и обновите примеры вместе с `openapi.yaml`.
